# React Native OTA Updates (Beta)

React Native OTA updates let an installed host app load newer Metro Module Federation remote bundles without releasing a new binary through the App Store or Play Store. Zephyr supports this flow with two packages:

- `zephyr-metro-plugin` publishes Metro Module Federation bundles to Zephyr Cloud and resolves remote manifests for `ios` and `android` builds.
- `zephyr-native-cache` runs in the host app, verifies remote bundle hashes, stores valid bundles on device, polls remote manifests for changes, and exposes APIs to apply downloaded updates.

:::warning Beta
Published packages support the flow below. The current upstream Metro guide still marks its integration experimental, including limits around custom Metro configurations.
The beta designation remains until an explicit maturity decision changes it. Package publication alone does not establish general availability.
See [runtime support and source evidence](/features/ota-updates) for versions, coverage, and the remaining decision.
:::

:::warning Native Code Boundary
OTA updates only update JavaScript bundles loaded through Metro Module Federation. Native code changes, new native modules, native dependency linking changes, permission changes, and host-shell changes still require a normal app-store release.
:::

For an Expo host, first check [Expo and Metro OTA Prerequisites](/integrations/expo).
The [`zephyr-native-cache-test` example](https://github.com/ZephyrCloudIO/zephyr-native-cache-test) provides a host app, two remotes, local OTA fixtures, update controls, and rollback scenarios.

## How It Works

1. You run a Zephyr-wrapped React Native CLI or RNEF `bundle-mf-remote` command.
2. The command uploads the Metro Module Federation artifacts, and Zephyr Cloud creates an immutable version with platform-specific artifacts and an `mf-manifest.json`.
3. Your released host app resolves a remote manifest through a Zephyr dependency such as `zephyr:profile@production`.
4. `zephyr-native-cache` reads bundle hashes from the manifest through its Module Federation runtime plugin.
5. When a remote is loaded, the cache layer downloads the bundle natively, verifies its SHA-256 hash, caches it on device, and evaluates it.
6. Background polling or a manual update check fetches known manifests again. If hashes changed, the cache layer pre-downloads the new bundles.
7. Apply downloaded updates through a JavaScript reload, either automatically after a download or at an application-defined point.

Next-launch loading, a user prompt, and immediate JavaScript reload are supported timing policies.
The cache does not replace modules already evaluated in the running JavaScript context.

Rollbacks use the same loading and application flow. A mutable environment or tag URL must resolve to the older release before a check can detect it.
A fixed version URL does not change after an environment rollback. The host must resolve the selected release again to apply it.

`withZephyr()` configures remote resolution; it does not publish an OTA version. See [Metro configuration and publication](/bundlers/metro#configuration-and-publication) for the upload boundary, Git identity inference, and explicit `zephyr.config.ts` overrides.

## Install Packages

Install the Metro and Module Federation packages in every host and remote app:

<PackageManagerTabs command="add --dev zephyr-metro-plugin@^1.8.0 @module-federation/metro@^2.9.3 @module-federation/runtime" />

Install the native cache package in the host app. Rebuild the native binary after linking it:

<PackageManagerTabs command="add zephyr-native-cache@^1.8.0" />

For iOS, run CocoaPods after adding `zephyr-native-cache`:

```bash
cd ios
pod install
```

## Configure The Host

Add the native cache runtime plugin to the host's Module Federation config. The plugin extracts bundle hashes from remote manifests and registers the manifest URLs that polling will check later.

```js title="apps/host/metro.config.js"
const { getDefaultConfig, mergeConfig } = require('@react-native/metro-config');
const { withModuleFederation } = require('@module-federation/metro');
const { withZephyr } = require('zephyr-metro-plugin');

const useZephyrRemotes = process.env.ZEPHYR_REMOTE_RESOLUTION === '1';

const remotes = {
  profile: useZephyrRemotes
    ? 'zephyr:profile@production'
    : 'profile@http://localhost:8082/mf-manifest.json',
};

const mfConfig = {
  name: 'mobileHost',
  remotes,
  shared: {
    react: {
      singleton: true,
      eager: true,
      requiredVersion: '19.1.0',
      version: '19.1.0',
    },
    'react-native': {
      singleton: true,
      eager: true,
      requiredVersion: '0.80.0',
      version: '0.80.0',
    },
  },
  shareStrategy: 'loaded-first',
  runtimePlugins: [require.resolve('zephyr-native-cache/runtime-plugin')],
};

const mfFlags = {
  flags: {
    unstable_patchHMRClient: true,
    unstable_patchInitializeCore: true,
    unstable_patchRuntimeRequire: true,
  },
};

async function getConfig() {
  const baseConfig = mergeConfig(getDefaultConfig(__dirname), {
    resolver: { useWatchman: false },
  });

  const zephyrConfig = await withZephyr({
    name: mfConfig.name,
    remotes: mfConfig.remotes,
    target: process.env.ZEPHYR_TARGET === 'android' ? 'android' : 'ios',
  })(baseConfig);

  return withModuleFederation(zephyrConfig, mfConfig, mfFlags);
}

module.exports = getConfig();
```

Use local HTTP manifest URLs during development. For Zephyr resolution, use selectors such as `zephyr:profile@production` or `zephyr:profile@staging`.
Use selector URLs when an installed host must follow later releases. `dependencyUrlMode: 'version'` pins resolved URLs and does not follow later environment changes.
See [Remote Dependencies](/features/remote-dependencies) for URL modes.

A dependency selector resolves remote entries during publication. To change the host's remote overrides and public variables after installation, configure the runtime manifest below.

You can also declare the same dependency in the host `package.json` so Zephyr dependency relationships are visible in the dashboard:

```json title="apps/host/package.json"
{
  "name": "mobile-host",
  "zephyr:dependencies": {
    "profile": "zephyr:profile@production"
  }
}
```

For more dependency selector options, see [Remote Dependencies](/features/remote-dependencies).

## Follow The Host Environment

Zephyr 1.8.0 includes `runtimeManifest` for a host shell whose JavaScript ships inside the native binary.
It lets that host follow an environment's remote overrides and `ZE_PUBLIC_*` values without rebuilding the binary.

Add the option to the `withZephyr()` call above:

```js
const zephyrConfig = await withZephyr({
  name: mfConfig.name,
  remotes: mfConfig.remotes,
  target: process.env.ZEPHYR_TARGET === 'android' ? 'android' : 'ios',
  runtimeManifest: '@production-${target}',
})(baseConfig);
```

Use plain quotes around the selector. Zephyr replaces `${target}` with `ios` or `android`.
Create the corresponding platform labels before bundling. Publication fails if the runtime label does not exist for that platform.

With the native cache registered, the first remote request applies the host manifest stored by a previous session.
It then refreshes that manifest in the background for the next launch or `ZephyrNativeCache.reloadApp()`.
The first launch keeps build-time remotes and values while storing the fetched manifest.
Without the native cache store, the host keeps its build-time configuration.

This flow keeps host configuration stable during a session. A reload before the background write completes may still use the previous configuration.
Cache polling and `checkForUpdates()` check known remote bundle manifests. They do not force a refresh of this host manifest.
See the [implementation and root manifest tests](/features/ota-updates#release-and-implementation-evidence).

## Register The Cache At Startup

Register the native cache before any remote bundle can load. In a Metro Module Federation host, this usually means registering it in `index.js` before `AppRegistry.registerComponent`.

```js title="apps/host/index.js"
import ZephyrNativeCache from 'zephyr-native-cache';
import { withAsyncStartup } from '@module-federation/metro/bootstrap';
import { AppRegistry } from 'react-native';
import { name as appName } from './app.json';

ZephyrNativeCache.register({
  enablePolling: true,
  pollIntervalMs: 5 * 60 * 1000,
  maxCacheSizeBytes: 50 * 1024 * 1024,
});

AppRegistry.registerComponent(
  appName,
  withAsyncStartup(
    () => require('./src/App'),
    () => require('./src/Fallback'),
  ),
);
```

Production builds enable the cache automatically. Development builds keep the cache disabled by default so normal Metro development behavior is preserved. Set `forceCacheInDev: true` only when you intentionally want to debug OTA behavior against Metro dev servers.

## Configure Remote Builds

RNEF projects must use the Zephyr RNEF plugin so `rnef bundle-mf-remote` and `rnef bundle-mf-host` upload Metro artifacts to Zephyr after the Module Federation build completes. React Native CLI projects must register the equivalent Zephyr-wrapped commands described in the [Metro bundler guide](/bundlers/metro#react-native-cli-publication-commands).

```js title="apps/remote/rnef.config.mjs"
import { platformAndroid } from '@rnef/platform-android';
import { platformIOS } from '@rnef/platform-ios';
import { pluginMetro } from '@rnef/plugin-metro';
import { zephyrMetroRNEFPlugin } from 'zephyr-metro-plugin';

export default {
  bundler: pluginMetro(),
  platforms: {
    ios: platformIOS(),
    android: platformAndroid(),
  },
  plugins: [zephyrMetroRNEFPlugin()],
};
```

Then publish a remote for each platform you support:

```bash
# iOS remote build and upload
rnef bundle-mf-remote --platform ios --dev false

# Android remote build and upload
rnef bundle-mf-remote --platform android --dev false
```

Running `start`, `run-ios`, or `run-android` is not publication. After the first `bundle-mf-remote` upload completes, verify in the Zephyr dashboard that the remote application exists and has a version before configuring an OTA environment or tag.

The host must resolve the same platform that the remote was published for. `withZephyr({ target: 'ios' })` resolves iOS remote artifacts, and `withZephyr({ target: 'android' })` resolves Android remote artifacts.

## Apply Updates In The App

Choose the timing policy for the installed host. The cache supports background downloads, an application prompt, or an immediate JavaScript reload after a changed bundle downloads.
For next-launch updates, use `downloadOnly` and resolve the selected release on the next launch.
For an in-session update, reload JavaScript at an approved point. This does not terminate the native application.

Use `useCacheStatus` to drive an update prompt:

```tsx title="UpdateBanner.tsx"
import { Button, Text, View } from 'react-native';
import ZephyrNativeCache, { useCacheStatus } from 'zephyr-native-cache';

export function UpdateBanner() {
  const { latestUpdateEvent, status } = useCacheStatus();

  if (!latestUpdateEvent && status.pendingUpdates.length === 0) return null;

  return (
    <View>
      <Text>Update ready</Text>
      <Button
        title="Reload now"
        onPress={() => ZephyrNativeCache.reloadApp()}
      />
    </View>
  );
}
```

Use manual checks when you want a pull-to-refresh, settings, or internal QA flow:

```ts
import ZephyrNativeCache from 'zephyr-native-cache';

await ZephyrNativeCache.checkForUpdates({ policy: 'downloadOnly' });
```

Use `downloadAndApply` only when an immediate JavaScript reload is acceptable:

```ts
await ZephyrNativeCache.checkForUpdates({ policy: 'downloadAndApply' });
```

`downloadAndApply` triggers the native React Native reload path only when that check downloads at least one changed bundle.
If polling already downloaded the update, use `reloadApp()` to apply it. A later check with no downloads does not trigger a reload.
Persist required UI state before either reload path.

Automatic polling defaults to `downloadOnly`. It polls only manifests registered while resolving remotes, not every remote in your project.

## Runtime Behavior

When a remote bundle loads, the cache layer returns one of these statuses:

| Status       | Meaning                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------- |
| `cache-hit`  | A verified bundle with the expected hash was loaded from disk.                                    |
| `downloaded` | The bundle was downloaded, hash-verified, stored on disk, and evaluated.                          |
| `skipped`    | The cache could not use the bundle, so Module Federation falls back to the normal network loader. |

The cache returns `skipped` when it cannot use a bundle, including missing hashes, hash mismatches, or unavailable native operations.
The normal Module Federation network loader can then run. Hash mismatches are not cached.
This hash check controls cache admission. It is not signature verification or a guarantee that the fallback network loader checks the hash.

The default cache limits are:

| Option              | Default     |
| ------------------- | ----------- |
| `enablePolling`     | `true`      |
| `pollIntervalMs`    | `5 minutes` |
| `maxCacheSizeBytes` | `20 MB`     |
| `maxAgeMs`          | `7 days`    |
| `forceCacheInDev`   | `false`     |

The cache evicts stale bundles with an LRU policy on cold start. Fresh bundles are preserved even if the cache is temporarily over the size limit.

## Deploy And Roll Back

Choose the environment policy before publishing:

- A version-based environment requires an explicit deployment of the selected version.
- A tag-based environment advances automatically when its conditions select a newer version.

`ZE_ENV` labels builds. A matching tag policy can use that label to release automatically.
See [release policies](/features/ota-updates#choose-the-release-policy).

To release an OTA update:

1. Publish a new remote version for `ios` and `android`.
2. Deploy the version explicitly, or let the configured tag policy advance the environment.
3. Wait for polling or call `ZephyrNativeCache.checkForUpdates()`.
4. Prompt the user or call `ZephyrNativeCache.reloadApp()` when your app is ready to apply the downloaded update.

To roll back, select the previous version for the environment that the host follows.
A subsequent manifest check can download its bundles. Apply them through the same reload flow.
Host manifest overrides follow the stored-manifest timing described above. Offline clients cannot receive the changed target until they reconnect.
Lock an automatically advancing environment during an incident if later builds must not replace the rollback.
See [rollback propagation](/features/ota-updates#rollback-propagation) and [environment locks](/features/locking-tags-environments).
